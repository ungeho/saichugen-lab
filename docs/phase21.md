# Phase 21：Codex Strategy Arena

## 目的と基準版

検証済みのTheoryと探索器を組み合わせた宣言JSONから、複数の戦術仮説を作り、条件を固定した3人対戦で記録する。名前や説明は仮説であり、強さを保証しない。ゲームルール、勝者判定、累計得点、終局報酬は変更していない。

Phase 20は `cf86d05c194b56254dfb97cd63252546e07c5e7d`、メッセージ「戦術仮説を個別検証できるTheory Labを追加」で通常commit・push済み。Phase 21の実験はこのSHAを基準版とし、実行中のソースhashと実行環境も保存する。Phase 21自体は未commit・未push。

## 構成と再利用

- `strategies/declarative.py`：Pydantic定義、内容hash、局面規則、追記型SQLite登録、既存選択器への変換。
- `strategy-definitions/*.json`：Codexが考案した初期5候補。コードや独立の評価式を重複実装していない。
- `experiments/arena.py`：参加設定を固定したリーグ、役割別乱数、席別統計、人工局面比較。
- `experiments/arena_cli.py`：JSONプリセットの見積もり・実行・結果保存。
- `features/arena/`：候補説明、派生JSON作成、版登録、リーグ計画、履歴、結果・判断の表示。

Theory Registry、TheoryPolicy、TheorySearch、HybridSearch、不完全情報サンプラー、`_play_game`、終局報酬関数、全6役割順、配札クラスタ統計、既存ExperimentStoreとQualityJobsを再利用した。QualityJobsは実験種別・モデル・実行器等を差し替えられる最小限の拡張とし、既存探索品質の既定動作を維持する。

ブラウザ回帰検証で、履歴イテレータの読取ロックと新規保存が待ち合うSQLite問題を検出した。ExperimentStoreは行を取得して接続を閉じた後に履歴を返す。スキーマ・旧データを変更せず、走査途中の保存もテストする。

## 戦略JSONの仕様

正確な機械可読スキーマは `GET /api/arena/schema`。実際に登録できる例は初期5JSONを参照する。主要項目は次のとおり。

| 項目 | 意味・制約 |
| --- | --- |
| schema_version | 現在1 |
| id / name / version | 安定ID、表示名、数値3要素の版。IDは英小文字・数字・下線 |
| creator / description / hypothesis / rationale | 作成者、説明、中心仮説、考案理由 |
| expected_strengths / expected_weaknesses | 予想。観測結果とは区別する |
| difference_from_existing | 既存戦略との違い |
| theory_config | 既存TheoryConfig。未知ID・未知パラメータ・不正重みを拒否 |
| rules | 最大12個。列挙型の局面条件と定義済みTheoryの重み変更のみ |
| selection | theory / theory_search / theory_search_adaptive / uniform / heuristic / adaptive / combined |
| total_budget | 直接選択ではnull。探索では1〜256の整数 |
| continuation | 既存の軽量5戦略のみ。探索AIの再帰呼出しを禁止 |
| seed_mode | evaluator_rng または fixed_policy |
| fixed_policy_seed | fixed_policyのときだけ0〜2^53−1の整数 |
| parent | 親ID・版・内容hash。初期候補はnull |
| change_summary / change_reason | 親からの変更点・理由 |
| created_at | タイムゾーン付き日時。UTCへ正規化 |
| definition_hash | 自身のhash欄を除く正規化JSONのSHA-256。省略時に計算、指定時は一致必須 |

重みは−2〜+2、Theory数・パラメータ範囲は既存TheoryConfigで検証する。規則は序盤（turn 0〜4）・中盤（5〜9）・終盤（10〜14）、現在の累計得点のlow/middle/high/tied、ラウンド範囲1〜5を照合し、**最初に一致した1件だけ**適用する。同点者がいれば自身のscore_positionはtied。規則は未定義Theoryを追加したり、無効なTheoryを有効にしたりしない。

直接評価ではTheoryの代理点が最大の札を選ぶ。Theory探索では代理点を配分へ使い、最終選択は既存の期待終局報酬に従う。uniform等の既存Hybrid方式はTheoryを使わないため、無効な設定を黙って受け入れず、Theoryや規則の併記を拒否する。任意コード、式、shell、file、外部パス、評価seed等の追加欄も拒否する。入力サイズ・範囲には上限を設けるが、OSレベルの隔離実行ではない。

## Codexが考案した5候補

すべてv1.0.0、直接評価、未検証。詳しい考案理由・強み・弱みはJSONとArena詳細に一元化した。

| ID | 中心思想と設定 | 有利と予想する状況 / 予想する弱点 |
| --- | --- | --- |
| codex_reserve | 強い札.6、中程度の札1、ラウンド.25。将来の選択肢を温存 | 先の選択肢が重要 / 目前のラウンドを取り逃す |
| codex_round_driver | ラウンド1、公開記憶.25。現在のラウンドの中間へ寄せる | 現在の順位調整 / 全体得点の偏り |
| codex_score_planner | 累計逆算1、ラウンド.35。残りを均等仮定して最終順位を意識 | 累計が偏った中終盤 / 均等仮定が外れる相手 |
| codex_opponent_reader | 相手目標1、公開記憶.25。公開得点から相手の目標を仮定 | 相手も得点調整する場合 / Randomや仮定と異なる相手 |
| codex_adaptive_theorist | 基本は中程度温存・ラウンド・累計各.5。得点上位は累計1.5、ラウンド.25、温存.1。序盤は温存1.2、ラウンド.3、累計.1。終盤は温存.1、ラウンド.7、累計1.2 | 局面ごとに重視点が変わる / 手で決めた条件・重みが過適合する |

Opponent Readerは**行動履歴から学習した相手モデルではない**。既存Theoryで表現できる公開得点からの目標仮定を用いた。実際の選択傾向を学習し更新する新思想は未実装候補として残す。Adaptiveの得点上位条件は序盤・終盤より先に照合する。

## 版と系譜

`strategy_definitions`テーブルへ定義を追記する。同じID・版・hashの再登録は同一と扱い、内容の違う同一版は拒否する。親は登録済み版と一致するhashに限定し、前向き参照と自己参照を拒否するため循環を作れない。過去実験は変更しない。

APIカタログは親・直接の派生版・その版を対象候補にした実験IDを返す。実験設定には対象・相手とも定義全文とhashを保存する。UIから版の過去実験を開き、条件・評価結果を確認できる。これは自動進化・自動採用ではない。

初期5候補は戦略レジストリにも登録され、通常対局・観戦・図鑑・同一局面比較・通常実験でplain IDを選択できる。UIで追加したカスタム版はArenaの`id@version`で選択する。通常対局のレジストリをDBごとに変更しないため、カスタム版の通常対局への動的反映は今回の対象外。

## 評価環境と情報の境界

宣言戦略には自身の定義のコピー、本人の観測、方策rngだけを渡す。評価計画、SQLite、Game、相手の実手札、配札seedは渡さない。操作は許可済み選択器の生成だけで、定義JSONにゲーム・報酬・結果・統計・他の定義を変更する経路はない。既存の探索は本人の観測から手札候補を一様サンプリングし、行動モデルで重み付けした完全な情報集合推論とは主張しない。

配札rngと方策rngは別。方策rngは `policy_seed`＋配札の**番号**＋役割から導出し、実際の配札seedを混ぜない。設定間で同じ役割の初期rngを共有するが、判断による乱数消費差までは揃わない。fixed_policyは自身の固定方策seedと観測JSONから導出する。実際の配札seedを変えても方策rng初期状態が変わらないことをテストした。

管理用の実験設定・エクスポートには再現のため配札seedを保存する。これを戦略の観測に含めない。ローカル利用者から評価seedを秘密にする認証システムではなく、戦略への引き渡しを防ぐ設計である。既存の信頼済みPythonプラグイン全体を悪意あるコードから隔離する仕組みではない。

## リーグと統計

各参加候補に対して、指定した相手2役を固定し、3役の全6順列を共通配札で対戦する。同じ戦略の相手2席参加も可能で、役割・座席を別に保存する。全組合せ総当たりやEloではない。対戦相手構成ごとの実験を分け、無条件に合算しない。

保存項目は実験ID、基準SHA、ソースhash、定義全文、seed区分、配札ID、役割順、席、戦略版、3席の累計点・勝者・報酬、判断時間・Rollout数、未完了状態。旧実験テーブルは保持し、Arenaを別experiment_kindとして扱う。

主評価は平均終局報酬。勝者集合から計算し、累計点には加算しない。単独勝利率、共同勝利率、敗北率、平均累計点、時間平均・中央値・p95・最大、Rollout数、席別成績も確認できる。役割別計測はJSONに保存する。

同一配札の全6役割順が正しい条件で揃った結果だけを使い、その6件の平均を1独立標本とする。区間は既存の配札平均を単位とする2,000回百分位ブートストラップ。10配札未満・分散0では未提供、10〜19配札は参考値。多重比較・候補選択の偏りは補正しない。

保存実験間は、基準SHA・ルール・報酬・情報条件・実装hash・相手定義・policy seed・seed区分・配札順序を照合する。配札番号から方策rngを作るため、同じ配札が一部あるだけでは対応比較にしない。総予算・継続戦略・予算方式等が異なる対応比較も拒否する。直接評価と探索AIは同じ計算量ではなく、リーグの点推定と時間を並べても同予算の優劣とは解釈しない。

## UI・API・再実行

通常起動は従来どおり。

```powershell
powershell.exe -ExecutionPolicy Bypass -File .\scripts\dev.ps1
```

「Strategy Arena」で候補を選び、説明・Theory・局面規則・版・hash・系譜を見る。「この版から派生JSONを作る」で編集用別版を作り、必要なら新規登録する。元定義は変更しない。

参加候補、相手2役、独立配札数、seed区分、評価者用offset、独立した方策seedを設定し、まず見積もる。探索AIは明示的な高コスト許可が必要。実行後は進捗・中断、保存履歴、結果JSON、対応比較、席別成績、公開人工局面の判断内訳を確認する。

主要APIは `/api/arena/strategies`、`/schema`、`/definitions`、`/estimate`、`/studies`、`/studies/{id}`、`/studies/{id}/cancel`、`/studies/{id}/export`、`/compare`。実行は202、同時Arenaジョブは409、不正設定は422。エクスポートは解決済み定義を含む結果JSONであり、そのまま開始APIにPOSTする形式ではない。プリセットは開始要求形式で再実行できる。

CLIはリポジトリルートから、初期セットアップ後に実行する。既定では見積もりだけで、`--run`を付けた場合のみ対戦する。

```powershell
$env:PYTHONPATH='backend/src'
uv run --project backend python -m strategy_arena.experiments.arena_cli --config experiments/presets/arena-stage1.json --database research-local/arena.sqlite
uv run --project backend python -m strategy_arena.experiments.arena_cli --config experiments/presets/arena-stage1.json --database research-local/arena.sqlite --output research-local/arena-stage1.json --run
```

`stage2`、`stage3`も同じ方法。保存時点のJSONには設定と定義全文がある。別環境では初期JSON・カスタム登録版・同一ソースを揃え、保存された版/hashと一致することを確認する。計測時間や実験IDは再現対象外。

上限は参加8、独立配札20、360対局、概算25万Rollout、時間1〜300秒。規模により小さい方が制約になる。探索定義は総予算256まで。見積もりは人工局面の探索も含む未校正モデルで、容量はJSONだけ。進捗は対局単位、停止は既存の協調方式で、1回の探索内部を即時中断するものではない。Arena内は同時1件だが、他の探索品質・分岐実験との全体同時実行数やメモリは隔離していない。

### 判断の違い

ゲームseed42で12ターンを各席の先頭合法手で進めた**公開人工局面**を使用。評価配札や未来の実手札を使って局面を選別していない。Stage 2では温存・累計逆算・局面切替がQ♠、ラウンド・相手目標・Heuristic・ScoreAwareがJ♥、RandomがJ♠を選んだ。各候補の評価と内訳を保存しUIで展開できる。同じ札や同じ成績が一部で観測されても、異なる設定が恒常的に別の行動をする保証はない。

## 制限とPhase 22への準備

- 自動生成・自動改良・自動採用は未実装。手でJSONを登録し実験する。
- Opponent Readerの学習、完全情報モード、複数相手構成の一括総当たり、Eloは未実装。
- カスタム版の通常対局への動的反映は未実装。Arenaには版指定で反映される。
- カタログの検証状態は常に「未検証の仮説」。ゲーム完了が強さの立証を意味しないため、自動で認定しない。
- 履歴と定義の全件読込はローカル小規模向け。大量履歴のページングは将来課題。
- UIの時間・探索回数は主に対象役。相手役を含む全席の生計測は結果JSONへ保存する。

Phase 22では親hashを固定した新しい版と、変更理由・事前仮説を登録し、開発用で調整、検証用で確認、最終評価用で一度だけ確認する運用を推奨する。検証・最終評価を繰り返し見て重みを変えた場合は、その集合を開発用として扱い、新しい未参照配札を確保する。現状のseed区分は範囲検証であり、利用者の閲覧や過学習を強制的に防ぐものではない。候補の不利な結果・中断・変更前版も保存し、採用の判断は人間が行う。

自由なPython生成を将来扱う場合は、専用プロセス・読み取り専用評価器・観測JSONのみのIPC・CPU/実時間/メモリ上限・ファイル/ネットワーク拒否・結果の再検証が必要。今回の宣言方式を、任意コードに対する安全なサンドボックスとみなさない。
