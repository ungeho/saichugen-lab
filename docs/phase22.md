# Phase 22：Strategy Evolution（戦略進化実験室）

## 目的と基準版

宣言戦略の生成、実験、選抜、検証、採用を別操作にし、親より有効な改良なのかを記録する。自動進化・自動採用・外部LLM呼出しは行わない。ゲーム進行、勝者判定、累計得点、終局報酬、既存戦略の評価処理は変更しない。

Phase 21は `83fc2f1fb2c79892a463d75783cbe9c46c73df62`、メッセージ「宣言的戦略とCodex Strategy Arenaを追加」で通常commit・push済み。Phase 22は未commit・未pushで残す。

## 構成

- `experiments/evolution.py`：生成設定・固定実験設定・採用基準、候補生成、進化実験、追記イベント、段階評価、開発用提案サマリー。
- `experiments/evolution_cli.py`：事前提案JSONの見積もり・開発実行・任意の検証実行。
- `experiments/evolution-candidates/`：Codexの事前仮説と宣言JSON。定義本体と実験設定を一組で保存する。
- `features/evolution/`：生成・登録・計画・選抜・検証・採用・系譜・履歴の画面。

Phase 21のStrategyDefinition・DefinitionStore・ArenaPlan・ArenaJobs・共通配札・全6役割順・終局報酬・配札クラスタ統計を再利用する。進化用に対局エンジンや独自の統計計算を作り直していない。

## 数値・構造的生成

`Generation`の主要設定は、親の`id@version`、専用seed、候補数1〜4、変更幅（0より大きく1以下）、操作リスト、タイムゾーン付き作成日時、子版の最初のpatch番号。作成日時も入力に含め、同じ入力なら定義hashまで再現する。UIでは現在時刻を入れるため、再現時は生成済みJSONの時刻も保存する。

許可操作はTheory重み、有効・無効、局面別重み、局面条件の追加・削除、Theory直接選択/探索/適応探索への変更、探索予算の±16変更。重みは±2、探索予算は1〜256、規則は12件まで。探索方式の自動変更時の予算は32。任意の式・コード・ファイル操作は受け付けない。継続戦略等の手動変更は既存宣言JSONの検証範囲内で可能。

親から毎回コピーを作り、1候補につき1種類の操作を適用する。行動設定（Theory、規則、方式、予算、継続、乱数方式）の正規化hashで親・他候補との同設定を除外する。生成は最大200回で打ち切り、要求数が得られなければ失敗する。設定が異なっても実際の全局面で異なる行動になる保証はない。

生成は登録や対戦を行わない。生成JSONを確認して明示的に登録する。同じID・版の上書きは禁止。既存の子版がある場合はpatch番号を変更する。無理に新しい式を既存Theoryへ押し込まず、未知の思想は別の研究候補とする。

## Codex改善提案

開発評価完了後に「Codex改善提案用JSONを保存」できる。親定義、開発集計、相手構成、判断時間、既知の弱点、事前仮説、許可された変更項目を渡す。局面別傾向は未計測と明示し、推測で補わない。

検証・最終結果、評価計画、生の対局データ、配札seed/ID、実際の隠し手札は提案入力に含めない。集計の対応配札IDも除く。評価用配札rngは戦略の方策rngと分離したままである。管理用エクスポートには再現用seedがあるが、戦略APIや提案サマリーとは経路が異なる。

Codexからは改善理由を含む別版のStrategyDefinition JSONを受け取る。UIはJSON配列の入力、APIは1定義ずつの取込。必ず既存スキーマ・親hash・版を検証する。外部API・認証・任意コード実行は追加しない。

## 再現可能なEvolution Experiment

作成時に親・子の定義全文とhash、変更差分、事前仮説・期待効果・副作用、相手2役、各段階のseed区分・offset、独立配札数、方策seed、時間上限、採用基準を固定する。全子は同じ直接親と一致するhashを持ち、親や他の子と同じ行動設定は拒否する。

設定hashは固定内容の正規化JSONから作る。実験IDと実験作成時刻は除外するため、同じ固定内容で別実験を作っても設定hashは同じになる。候補定義内の作成時刻は定義の一部である。schema_version=1、assessment_version=evolution-policy-v1、Phase 21基準SHAを記録する。Arena自身の既存基準SHAも保存し、進化基盤の基準版と区別する。

SQLiteに次を追加する。既存テーブル・旧データは変更しない。

| テーブル | 内容 |
| --- | --- |
| evolution_experiments | 固定設定・定義・差分。追記のみ |
| evolution_events | 段階要求・開始・開始失敗・明示判定。時刻付き追記のみ |
| evolution_final_seeds | 最終seedの予約。seedを主キーとし再利用を拒否 |

対局中の進捗と結果は従来のArenaレコードへ保存し、進化イベントから実験IDで参照する。確定済みの定義・過去段階を上書きするAPIはない。読込時に保存済み結果から状態・証拠を組み立て、親子報酬、対応差、判断時間を表示する。

## 段階と状態

1. **Candidate**：生成・登録した候補。評価計画作成だけでは実行しない。
2. **Development Tested**：開発用の全候補対戦が完了。親と同じ配札・相手・席順で比較する。
3. ユーザーが候補を選び、別区分の検証配札へ進める。
4. **Validation Passed**：固定した検証基準を満たす。満たさなければ**Inconclusive**。
5. 検証通過候補だけ最終評価へ進める。最終評価も基準を満たし、ユーザーが理由付きで明示操作した場合だけ**Promoted**。
6. **Rejected**：ユーザーが理由付きで棄却。採用・棄却の確定判定は変更しない。**Inconclusive**は明示保留としても記録できる。

少数配札の負の差だけで自動棄却はしない。前段階が未完了の候補・段階に選抜されなかった候補を次段階へ追加しない。各段階は1実験で一度だけ要求でき、中断・失敗も別実験として残す。

最終seedは開始前のSQLiteトランザクションで予約する。既存の実験テーブルにある最終区分の配札と重複した場合も拒否する。開始失敗しても予約は解除しない。通常の混雑は予約前に409で拒否するが、予約直後の競合・プロセス停止では段階が消費される場合がある。結果を書き換えず別計画・新しい最終seedを使う。

最終結果を含む提案サマリーは提供しない。ただし管理者が結果を見て手動で最適化することを技術的に完全禁止する仕組みではない。既存Arenaを別途使う利用者の最終seedの再使用を全APIで強制禁止するものでもない。Evolutionでは同じDB内の予約・既存結果を照合する。

## 固定する採用基準

既定値は独立配札10件以上、子−親の平均報酬差が0超、対応差の95%区間下限も0超、判断平均時間が親の2倍以内、相手構成1種類以上。基準は実験作成後に変更しない。

同じ探索予算・予算方式・最低試行・継続条件等を満たさない場合は、Arenaの対応比較が拒否され、採用を通過できない。時間も実測する。検証と最終の両方で通過が必要。各段階間の戦略・対局ソースhash、ルール、報酬、情報条件、乱数方式の相違も通過を妨げる。

現在1実験は固定相手2役の1構成だけ。`min_opponent_compositions=2`を指定すると証拠不足として通過しない。複数相手構成を跨ぐ採用判定は未実装。1構成で採用されても絶対的な強さとは扱わない。

区間は既存の独立配札平均に対する2,000回百分位ブートストラップ。全6役割順が揃った配札だけを1標本とする。10件未満・分散0では区間なし、10〜19件は参考値。候補選抜・多重比較の偏りは補正していない。検証・最終を見て同じ集合に重みを合わせ直した場合、その集合は以降開発用として扱い、別の未参照配札を確保する。

## 画面とAPI

「Strategy Evolution」で親を選び、生成設定を指定して候補JSONを作る。手動提案も編集欄へ入力できる。検証して登録後、子候補を選んで実験計画JSONを作り、仮説・効果・副作用・基準を入力して保存する。

全候補時の見積もりを確認して開発評価を開始する。完了後、チェックした候補だけ検証へ進める。結果は段階別の表・対応差・時間で表示し、異なる区分の報酬を一本の「進化改善」線にはしない。親子のTheory・規則・探索設定のbefore/after、hash、理由、操作履歴も展開できる。履歴・結果JSON・提案JSONを保存可能。採用状態は通常対局の既定AIを自動変更しない。

| API | 用途 |
| --- | --- |
| POST /api/evolution/generate | 未登録の候補プレビュー |
| POST /api/evolution/import | 宣言JSONの検証・追記登録 |
| GET/POST /api/evolution/experiments | 履歴／固定計画作成 |
| GET /api/evolution/experiments/{id} | 設定・系譜・進捗・状態・証拠 |
| POST /api/evolution/experiments/{id}/stages/{stage} | childrenを明示して段階開始 |
| POST /api/evolution/experiments/{id}/decision | 子・判定・理由の明示記録 |
| GET /api/evolution/experiments/{id}/proposal | 開発サマリーのみ |
| GET /api/evolution/experiments/{id}/export | 全条件・段階結果・イベント |

停止は既存 `/api/arena/studies/{arena_id}/cancel` を再利用し、UIから操作できる。協調停止なので探索1回の内部を即時停止しない。親子最大5設定、独立配札上限20、Arenaの最大360対局・25万Rollout・1〜300秒を適用する。上限の組合せによって要求を拒否する。ArenaとEvolutionは同じワーカーで同時1件。他の探索品質・分岐のプロセス全体を隔離するものではない。

## Codexの事前改良仮説

定義と実験前の理由は `experiments/evolution-candidates/*.json` に保存した。子は両方v1.0.10、親v1.0.0のhashを固定。今回の実験結果を見て仮説や重みを変更していない。

### 温存系

Phase 21開発2配札の低い点推定（−.833）は弱さの確証ではないが、目前の順位調整を逃す可能性を調べる動機とした。reserve_middleを1→.5、reserve_strongを.6→.3、round_focusを.25→.75へ変更する。現在ラウンドの調整改善を期待する一方、強い札・中程度の札を早く失い後半の選択肢が減る副作用を想定する。

### Adaptive Theorist系

得点上位時のcumulative_targetを1.5→1、round_focusを.25→.75、序盤のreserve_middleを1.2→.6、round_focusを.3→.6へ変更する。規則の照合順と条件は維持する。極端な重みを緩和し現在ラウンドとの両立を期待するが、温存・累計上位からの回避が弱くなる可能性がある。複数項変更なので個々の因果寄与は分離できない。

この案の事前理由にはPhase 21の既存開発・検証値の変動も参考情報として記録した。その既閲覧の旧検証配札を完全な未参照集合とは扱わず、今回の新しい検証offset400を候補固定後に使用した。今後の改善提案APIは開発集計だけを渡す。
