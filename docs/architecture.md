# 構成案と段階的実装

状態: 初期基盤を実装済み。GPCC資料・公開二次資料と承認済みの暫定仕様を採用。以下の構成案から必要な部分を順に実装している。

## 情報の境界

エンジンだけが全手札・未使用カード・未公開の提出札を保持する。Strategyには独立したObservationと専用乱数源だけを渡す。観測には自分の手札、合法手、公開履歴、公開得点、進行位置を含める。完全状態やそこへの参照は渡さない。

同時選択が確定した場合、全員が同じ公開局面から選択する。逐次計算しても先に選ばれた行動は後の戦略へ渡さず、3人の提出完了時に一括公開する。ブラウザにも相手の保留中の行動を送らない。

Decisionは選択カードと任意の説明・獲得意図・カード別評価を返す。意思決定時間はrunnerが計測する。GreedyとConservativeはターン獲得を増減する比較基準として定義し、ゲーム勝率の最適化と区別する。スートフォローなど初期プロンプト固有の制約は引き継がない。

## 再現と実験

配札と各戦略の乱数系列を分離する。シードに加え、デッキ順序、行動列、戦略名・バージョン・設定、コードリビジョン、ルールバージョン、実行環境、対戦相手、座席割当、学習モデル識別子を保存する。非公開の完全リプレイと対戦中の公開APIを分離する。

共通配札で座席割当を比較し、3戦略なら6順列を評価できるようにする。同時選択では先手位置を捏造せず、座席効果と提出順による情報漏洩がないことを調べる。学習と評価でシード集合とモデル更新を分離する。

個別勝率に加え、対戦相手構成ごとの成績を集計する。共同勝利の扱いはルール確定後に指標へ明記する。独立配札の勝率にはWilson区間、共通配札・座席入替の比較には配札を単位にした対応付き集計とクラスターブートストラップを検討する。累積勝率・直近N試合・得点分布・順位推移・計算時間を表示する。ターン得点とゲーム得点を別系列で表示する。

## 段階と完了条件

1. ルール確定: 一次資料、未確定項目への回答、具体的な判定例を仕様に記録。
2. エンジン: 配札の一意性、合法手、全カードの比較、得点各層、同点、終了、違法操作の非破壊性、観測情報の非漏洩、リプレイ一致をpytestで検証。
3. 最低限の対戦: 5戦略を実装。同一シードで履歴一致、全戦略が合法手を出すことを検証。
4. 人間用UI: APIとテーブル画面。選択・公開・得点更新をVitestとPlaywrightで検証。
5. 大量対戦: 保存・再実行・座席入替・共通乱数。小規模既知ケースとの一致と処理性能を確認。
6. 統計分析: 集計値を既知データで検証。短期のターン獲得と最終勝率を比較できる画面を完成。
7. 高度な戦略: Monte Carlo、ISMCTS、TDなどを個別追加し、評価用データを固定して比較。

全段階で該当するテストが通ってから次に進む。現在はゲームエンジン、5戦略、人間対戦・観戦UI、CLIバッチ対戦、SQLite保存、基本グラフまで実装。高度な学習・推論と詳細な行動分析は今後の段階。

## 方針の補足

厳密な学術研究のための統制やアクセス制御より、アルゴリズムの挙動を楽しめるシンプルな基盤を優先する。通常モードの観測は明確にするが、完全情報・カスタム情報の実験も将来追加できる。情報条件は結果へ記録し、比較画面で確認できるようにする。

初期版では情報条件imperfectだけを受理。実験中のStrategyに配札シードや完全リプレイを渡さないことは実装上の境界であり、任意Pythonコードを隔離するセキュリティ機構ではない。
